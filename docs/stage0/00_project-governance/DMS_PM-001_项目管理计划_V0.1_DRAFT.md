## 1. 管理原则

本项目采用以下 7 条核心管理原则，所有角色的活动必须以此为准则：

| 编号 | 原则 | 具体要求 |
|------|------|----------|
| P-01 | **过程受控** | 所有输出必须有输入来源、执行记录、验证证据 |
| P-02 | **基线先行** | 任何变更必须基于已冻结基线，不存在"隐式改动" |
| P-03 | **双向可追溯** | 每个需求向下可追到测试用例，向上可追到设计输入 |
| P-04 | **证据驱动** | 决策必须有数据/测试/评审记录支撑，拒绝经验主义 |
| P-05 | **分层治理** | 不同层级的决策由对应角色审批，不越级、不降级 |
| P-06 | **风险前置** | 风险识别早于执行，缓解计划早于问题发生 |
| P-07 | **AI 透明** | AI 生成内容必须标注、审核、留痕，关键决策不盲信 AI |

## 2. 研发基线体系（7 级）

### 2.1 基线定义

基线是项目过程中在特定时间点冻结的文档/数据集合，作为后续变更的参照基准。本项目定义 7 个基线等级，与阶段门对齐：

| 基线编号 | 基线名称 | 冻结时点 | 主要内容 | 阶段门 |
|----------|----------|----------|----------|--------|
| BL-1 | 需求基线 | S1 结束 | 产品需求规格书 (PRS)、用户需求 | 门 1→2 |
| BL-2 | 技术规范基线 | S2 结束 | 系统架构、技术方案、零件清单（初版） | 门 2→3 |
| BL-3 | 详细设计基线 | S3 结束 | CAD 模型、工程图、BOM v1.0 | 门 3→4 |
| BL-4 | 验证基线 | S4 结束 | 验证计划、测试用例、验收标准 | 门 4→5 |
| BL-5 | 设计输出基线 | S5 结束 | 验证通过的设计、DHF v1.0 | 门 5→6 |
| BL-6 | 生产基线 | S6 结束 | DMR、工艺文件、试制报告 | 门 6→7 |
| BL-7 | 发布基线 | S7 结束 | 最终交付物、合规文件归档 | 项目关闭 |

### 2.2 基线冻结规则

1. **冻结前置条件**：阶段门评审通过，所有必需交付物齐备
2. **冻结操作**：Git tag + Fusion 360 数据管理版本发布（Release）
3. **冻结后变更**：必须走正式变更控制流程（见第 6 节）
4. **基线保留**：所有历史基线必须完整保留，永不删除

## 3. 需求追踪规则

### 3.1 需求追踪矩阵 (RTM) 结构

每个需求条目必须具备以下追踪链：

```
用户需求 (UR)
  → 产品需求 (PR)
    → 设计输入 (DI)
      → 设计输出 (DO)
        → 验证方法 (VM)
          → 验证结果 (VR) ✅/❌
```

### 3.2 需求编号规则

| 编号类型 | 格式 | 示例 |
|----------|------|------|
| 用户需求 | UR-XXX | UR-001：设备可连续工作 30 分钟 |
| 产品需求 | PR-XXX | PR-001：连续工作时间 ≥ 30min@额定负载 |
| 设计输出 | DO-XXX | DO-015：电机选型为 XYZ-123（额定连续 45min） |
| 验证用例 | VM-XXX | VM-022：连续运行 30min 温升测试 |
| 验证结果 | VR-XXX | VR-018：实测 42min，温升 38K ✅ |

### 3.3 追踪完整性要求

| 阶段 | 追踪覆盖要求 |
|------|--------------|
| S1 | 所有 UR → PR 映射 100% 完成 |
| S2 | 所有 PR → DI 映射 100% 完成 |
| S3 | 所有 DI → DO 映射 ≥ 90% |
| S4 | 所有 DO → VM 映射 100% 完成 |
| S5 | 所有 VM → VR 执行 100%，✅ 通过率 ≥ 95% |

### 3.4 追踪矩阵维护

- **维护责任人**：AI-B（文档管理角色）
- **更新时机**：每次基线冻结、每次变更批准后
- **存储位置**：`docs/stage{N}/requirements/RTM_V{版本}.md`
- **审计检查**：每次阶段门必查 RTM 完整性

## 4. 评审机制

### 4.1 评审类型

| 评审类型 | 目的 | 参与角色 | 频次 |
|----------|------|----------|------|
| 日常技术评审 (DTR) | 技术方案交叉验证 | AI-C + AI-D + AI-E | 每完成一个设计单元 |
| 阶段性评审 (SR) | 阶段交付物评审 | 全部 AI 角色 + 人工审核 | 每个阶段中期 |
| 阶段门评审 (SGR) | 阶段进入/退出决策 | 全部角色 + 发起人 | 每个阶段门节点 |
| 变更评审 (CR) | 变更影响分析 | CCB 成员 | 按需触发 |
| 独立审核 (IA) | AI-E 独立检查 | AI-E（独立） | 关键节点 |

### 4.2 评审输出

每次评审必须产生**可审计记录**：

| 输出项 | 格式 | 内容 |
|--------|------|------|
| 评审记录 | Markdown 文件 | 评审人、日期、议题、讨论要点 |
| 决议项 | 编号列表 | 问题描述、决策内容、责任人、截止日期 |
| 行动项 | ACTION-XXX | 同上，加状态追踪 |
| 偏差记录 | DEV-XXX | 批准的偏离（需发起人签字） |

### 4.3 评审状态机

```
待评审 → 评审中 → 有条件通过 → 整改 → 重新评审 → 通过（✅）
                         ↓
                      不通过 → 打回修改 → 评审中
```

**关键规则**：阶段门评审必须全部"通过"才能放行；日常评审"有条件通过"可继续但必须跟踪整改。

## 5. 执行监控机制

### 5.1 进度跟踪

| 监控维度 | 频率 | 工具 |
|----------|------|------|
| WBS 工作包完成度 | 每周 | GitHub Projects 或 Issues |
| 基线版本状态 | 每个阶段 | Git tag + Fusion 版本 |
| 风险状态变化 | 每两周 | RSK-001 更新 |
| 待决事项进度 | 每周 | DEC-001 更新 |
| AI 任务执行 | 实时 | AI-001 任务单系统 |

### 5.2 健康度指标

| 指标 | 计算方式 | 警戒阈值 |
|------|----------|----------|
| 按时交付率 | 按时完成工作包 / 总工作包 | < 85% 触发告警 |
| 需求稳定度 | 变更需求数 / 总需求数 | > 15% 触发评审 |
| 风险闭环率 | 已关闭风险 / 总风险 | < 70% 触发告警 |
| 假设验证率 | 已验证假设 / 总假设 | < 80% 触发评审 |
| 基线偏离数 | 批准的偏离项 | ≥ 3 触发发起人评审 |

### 5.3 升级路径

```
发现问题 → AI-A 协调解决
    ↓ 48h 未解决
发起人介入决策
    ↓ 涉及范围/预算/质量重大偏离
CCB 召开紧急变更评审
    ↓ 失败
项目降级或暂停
```

## 6. 变更管理

### 6.1 变更控制委员会 (CCB)

| 角色 | 权限 |
|------|------|
| 发起人 | 主席，最终审批 |
| AI-A（项目负责人） | 变更申请受理、影响分析组织 |
| AI-E（独立审核） | 独立影响评估 |
| 人工审核（机械专家） | 技术影响评估 |

### 6.2 变更流程

```
1. 变更申请（CR-XXX）—— 填写变更描述、理由、影响
2. 影响分析 ———— 技术影响 + 进度影响 + 成本影响 + 合规影响
3. CCB 评审 ———— 决定批准 / 驳回 / 有条件批准
4. 执行变更 ———— 更新文档 + 触发相关工作包
5. 验证变更 ———— AI-E 独立验证变更已正确实施
6. 基线更新 ———— 重新冻结受影响的基线
7. 记录归档 ———— 所有变更记录存入决策库 (decisions/)
```

### 6.3 变更分类与审批权限

| 变更类型 | 定义 | 审批权限 |
|----------|------|----------|
| 微小变更 | 不影响功能/性能/合规，仅文案或格式 | AI-A 批准 |
| 次要变更 | 影响单一模块，不跨越基线 | AI-A + AI-E |
| 重大变更 | 跨越基线、影响性能/安全/合规 | CCB 全票 |
| 紧急变更 | 安全相关紧急修复 | 发起人临时批准，事后补流程 |

## 7. 质量保证框架

### 7.1 文件质量要求

| 要求 | 说明 |
|------|------|
| 完整性 | 所有必需章节必须填写，无"TODO"占位（阶段 0 文档可标记"待决"） |
| 可追溯性 | 所有事实/假设/设计输入/设计输出必须带分类标记 |
| 版本一致性 | 同一概念在不同文档中的表述必须一致 |
| 评审记录 | 每次关键修改必须附评审记录 |

### 7.2 设计质量门 (DQM)

每个阶段门除交付物检查外，还需满足以下质量门：

| 质量门 | 检查内容 | 工具 |
|--------|----------|------|
| DQM-1 需求完备性 | RTM 覆盖率、需求可测试性 | AI-E 自动化检查 |
| DQM-2 设计合理性 | 力学仿真、公差链、可制造性 | AI-C 分析报告 |
| DQM-3 合规性 | 法规标准符合性、风险管理完整性 | AI-E 合规矩阵 |
| DQM-4 验证充分性 | 测试覆盖率、通过率、证据充分性 | AI-E 验证审计 |

### 7.3 CAPA 流程

对于验证中发现的问题（❌ 结果），按以下优先级处理：

1. **安全相关** —— 立即 CAPA，最高优先级
2. **合规相关** —— 1 周内启动 CAPA
3. **性能不达标** —— 阶段门评审决定
4. **一般缺陷** —— 记录并纳入下个迭代
